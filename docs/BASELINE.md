# 六层基线与仓库入口

定稿：2026-09-27；盘点起点：f8a995467201ff26a51eb6dce644283de8e6d157。本文规定 **信息应该放在哪一层，以及不同层怎样互相约束**；不替代各层自己的现行文档。

## 六层语义主轴

| 层级 | 只回答一个问题 | 当前权威入口 |
| --- | --- | --- |
| L1 产品目标 | Agent World 要成为怎样的产品？ | [PRODUCT_POSITIONING](../PRODUCT_POSITIONING.md) |
| L2 系统不变量 | 无论怎么实现，哪些性质不能被破坏？ | [INVARIANTS](INVARIANTS.md) |
| L3 领域模型 | 系统里有哪些概念，它们是什么关系？ | [DOMAIN_MODEL](DOMAIN_MODEL.md) |
| L4 行为契约 | 什么操作合法，什么条件下发生什么状态变化？ | [FOUNDATION](FOUNDATION.md) 及能力合同 |
| L5 技术架构 | 哪些技术组件承担这些责任，边界和依赖如何组织？ | [ARCHITECTURE](ARCHITECTURE.md) |
| L6 具体实现 | 当前版本具体用哪些模块、存储、接口和部署方式兑现架构？ | [IMPLEMENTATION](IMPLEMENTATION.md) 与源码 |

越往下越具体。上层约束下层，但不是瀑布审批：来自实现、测试或 UX 的事实可以向上反馈，发现模型或不变量本身有问题时可以显式修改。**禁止的是静默反向改写，不是禁止反馈。**

这六层也不是六个强制目录、六个服务或六个团队。一个文件只要职责清楚，可以覆盖同一层内紧密相关的合同；不能为了层数对称制造空抽象。

## 横轴 A：验证证据

测试、实验、运行观察、兼容性检查和长期运行记录不是第七层。它们回答“某条声明在什么源码、环境和场景下得到什么证据”。

验证失败后先区分：实现缺陷、行为契约含糊、领域模型缺项、测试假设错误、环境问题，或上层目标／不变量确实需要重新讨论。不能为了让测试变绿，把原语义悄悄改成当前代码碰巧做得到的样子。

当前证据入口统一在 [REFERENCE_GATE](REFERENCE_GATE.md)；带日期的执行结果只说明当次覆盖，不自动变成产品定义。

## 横轴 B：交互与表现

交互／表现不是第七层，也不拥有独立业务事实。它负责让人和 Agent 正确理解 L3-L6 已经存在的概念、状态和因果关系，并把可用性问题反馈回设计。

表现必须遵守一条硬边界：客户端文案、动画、缓存、模型总结和读取进度可以 **表达** 服务端事实，不能 **创造** 服务端事实。具体要求见 [PRESENTATION](PRESENTATION.md)。

## 现行文档职责

| 文档 | 所属位置 | 唯一职责 |
| --- | --- | --- |
| PRODUCT_POSITIONING | L1 | 产品目标与范围，不存实现细节。 |
| INVARIANTS | L2 | 不能被实现便利破坏的系统性质。 |
| DOMAIN_MODEL | L3 | 概念、关系及必须保持的非等价关系。 |
| FOUNDATION | L4 | Runtime/SDK 的调用、事务、身份接入、版本与恢复合同。 |
| AGENT_INTERACTION | L4 | 外部 Agent 的结构化接入、回应、等待与恢复语义。 |
| WORLD_DATA | L4 | 数据归属、授权视图、快照与缓存合同。 |
| OBSERVATION_STREAMS | L4 | 公开观察、共享流、历史和现场游标。 |
| DURABLE_TIME | L4 | 可选持久 timer 的声明、执行、失败与恢复。 |
| RETENTION | L4 | 历史／通知保留与清理合同。 |
| ARCHITECTURE | L5 | 组件、依赖、进程与信任边界。 |
| IMPLEMENTATION | L6 | 当前版本的模块、数据库、传输和已知实现差距。 |
| PRESENTATION | 横轴 | UI／客户端如何忠实表达事实，不定义业务规则。 |
| REFERENCE_GATE | 证据横轴 | 什么需要验证、证据覆盖到哪里。 |
| OPEN_DESIGN | 附着项 | 未决事项按所属层标记，不自己成为一层。 |

历史审计、Commons、World Zero 等带日期材料是证据或示例，不覆盖上述现行入口。

## 两个典型问题怎样跨层追溯

### “确认”不是一句文本

L2 规定 Runtime 不能从自然语言替主体制造意愿；L3 区分 Operation、Receipt、Event、Business Object；L4 规定确认必须是世界声明的结构化操作并通过身份、资格和状态检查；L5 决定鉴权、网关、Runtime 和世界规则分别承担什么责任；L6 才决定具体 JSON、Python、SQLite 和 HTTP/MCP 形态。UI 最后只能忠实显示这些事实。

因此“用户发了一句我确认了，服务器就当确认”不是允许的技术解释；除非这句话只是某个已定义结构化操作中的文本字段，而真正的确认由协议动作和规则成立。

### 第三方／群众公裁

L1 记录这是产品允许和需要探索的方向；L2 约束不能由争议一方单方面伪造他方或裁决者结论；L3 只在机制确定后加入 Case、Evidence、Decision、Reviewer 等正式概念；L4 定义资格、提交、冲突、超时、复核和结果成立条件；L5/L6 再决定组件与实现。当前候选方案留在 OPEN_DESIGN，不因实现暂缺而消失。

## 变更规则

1. 改 L1/L2：必须明确说明为什么产品目标或系统不变量本身改变，以及哪些下层材料受影响。
2. 改 L3/L4：说明旧模型／语义、新模型／语义和迁移或兼容影响；不能只改测试期待值。
3. 改 L5：说明责任边界或依赖为何改变；文件拆分本身不自动算架构变化。
4. 改 L6：普通重构和修复只需保持上层合同并提供相应证据，不要求逐层改文档。
5. 改表现：不能通过文案或动画制造服务器没有提交的事实；UX 发现上层问题时按正常反馈重新讨论。
6. 改测试：删除或弱化已复现缺陷的回归时，必须说明对应合同为何失效或由什么等价证据替代。

最小变更记录只需要：**影响哪一层、依据是什么、行为影响、实际验证、尚未验证什么。** 不建立第二套审批系统或重复路线图。
