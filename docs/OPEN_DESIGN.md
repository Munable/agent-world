# 待设计、实现差距与待验证

更新：2026-09-26。这里不重复产品定义，也不把未来可能用到的能力全部列为必做。新增工作必须注明具体问题、归属及验收方式；以下不表示已有 API 或已经选定方案。

## 待设计

### 1. 通话与共同事项的接续合同

现有结构化函数、事件、回执、活动足以构建具体流程，但不等于通用对话逻辑已定稿。需明确：请求与回应引用；读取、确认、执行、完成的区分；并发／晚到回应；撤回、超时与重新发起；换客户端后取得哪些信息；通知保留期到达时未决事项如何处理。

先用最小非游戏交互逐步列出提交者、结构化输入、状态变化和失败分支，再决定哪些需要通用辅助接口。禁止直接新增全局对话轮次、统一审批状态机或所有动作必领的租约。

### 2. 第三方／群众公裁

这是明确的待做方向，不是“无法自动判断所以忽略”。参评者与其 Agent 在 Runtime 外部执行评审；服务器不解析自然语言证据得出裁决。

待定细节：案件与证据的数据合同、参与资格与任务分配、利益冲突、证据可见范围、结构化意见提交、有效裁决的成立条件、重复提交、超时／退出、复核及结果执行。尚未选择票数、权重、仲裁者或激励机制，不提前写成实现承诺，也不强制全部世界交互经过公裁。

### 3. 数据保留后的语义

需按数据用途确定保留与恢复边界，尤其是未决事项、操作回执、commit metadata、终态 timer ID。当前事件／历史清理不约束数据库总大小；不能直接删回执或去重记录，导致旧操作再次执行。先测增长与恢复，再决定压缩、归档、过期拒绝等合同，不提前引入大型存储平台。

## 待验证，不等于缺少新抽象

长期运行需观察连续操作、事件保留、未决事项、定时积压、重启与多次升级组合后的正确性、延迟和存储增长；还要验证备份恢复后接续。加速循环不等于真实运行数月，固定脚本不等于真实外部 Agent 行为。

缓存检查应包含过期／驱逐、权限变化、乱序响应和跨客户端恢复；通信检查应包含外部 Agent 完全停止后重新进入，以及响应丢失后同 ID 恢复。只对实际观察到的结果作结论。

## 不作为本轮前提

完整游戏、通用规则引擎、强制 Party／好友／背包对象、不可信插件沙箱、分布式托管、统一资产平台，不是本轮逻辑核对的先决条件。外部系统副作用及动态群体频道等有实际消费者时再另立合同；已有公开观察不能继续笼统列为“未实现”。

日常验证优先本地或可控机器；不以高频计费 CI 替代逻辑评审。保留必要的历史证据，不复制多份路线图。
