# L4：观察与共享事件流合同

复核：2026-09-27。本文定义显式公开观察、共享事件流、现场读取和历史读取的语义。它们用于观察已经发生的世界事实，不是伪造参与者或自动业务确认的机制。

## 公开观察必须显式

匿名／公开观察只有在世界明确声明某个 View 或 Stream 可以公开时才成立。公开观察不创建参与者身份、不借用其他主体凭据，也不获得世界写权限。

世界不能因为“这条数据以后可能要展示”就默认把私有状态公开；公开性必须属于声明的观察合同。

## 共享 Stream

世界可以声明有序共享 Stream，并为每个 Stream 定义公开性或读取授权。发布必须由已经获准执行的世界规则产生，而不是给匿名输入提供另一条旁路写入。

与某次 Command 同属一个 Runtime 提交的共享发布，应和该 Command 的状态／Receipt 一起成立或一起失败。重试同一已提交 Operation 不应重复发布同一逻辑事件。

当前授权如果在读取时已经撤销，就不能因为客户端还持有旧 cursor 继续获得新受保护事件。

Shared Stream 是观察渠道，不自动提供逐消息 ACK、任意群组成员关系、私信合并或完整聊天产品语义。

## 现场流、历史与游标

客户端取得 Snapshot 后，应从与该 Snapshot 一致的现场锚点继续读取，避免在 Snapshot 与后续事件之间跳过并发事实。

现场 cursor 用于继续向前读取；历史 cursor 用于向过去翻页。历史翻页不能替换现场进度，历史记录也不能重新伪装成刚发生的现场动作。

cursor 必须绑定 Stream、World Instance、viewer／credential 和相关版本上下文。伪造、错绑或过期 cursor 必须失败或要求 reset。

## Retention gap

共享流可以按明确保留策略清理旧前缀。客户端请求已经被清理的历史时，必须得到“历史被截断／需要 reset”的明确结果，不能把缺失历史解释为已读、已处理或业务自动结束。

清理共享 Stream 不应同时删除当前 State Fact、Receipt 或其他独立职责的数据；其他通知流的清理也不应偷偷清除共享 Stream。

## 客户端处理

客户端需要按稳定事件身份去重并保持声明的顺序。表现队列可以有界并丢弃已过期动画，但不能因此删除持久世界事实。

对话回复关系、确认关系和事项完成必须由世界 Domain Object 与 Command 规则验证，不能只根据相邻消息或自然语言文本推断。
